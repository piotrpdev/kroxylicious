= Enforcing minimum file permissions on confidential files

[role="_abstract"]
Kroxylicious validates that confidential files (TLS private keys, keystores, truststores, password files, and KMS credential files) are not accessible by group or other users, preventing accidental secret exposure through overly permissive filesystem permissions.

Similar to how the `ssh` command refuses to use a private key file that is world-readable, you can configure Kroxylicious to reject files whose permissions allow group or other access.

== Policy modes

Three policy modes are available for each category:

`STRICT`:: Files must be accessible only by their owner.
Permissions with any group or other read, write, or execute bits set are rejected.
This is equivalent to requiring `chmod 400` or `chmod 600` on confidential files.
Use this in production environments.

`RELAXED`:: Other-user access is forbidden, but group access is permitted.
This supports Kubernetes deployments where secrets are mounted with a group set via `fsGroup` in the pod security context, making file permissions such as `0440` acceptable.

`DISABLED`:: No permissions are enforced.
A warning is logged for files that would be rejected by `STRICT` or `RELAXED`, but startup is never rejected.
This is the default for all categories for backward compatibility.

== File categories

Policies are configured per category under `security.filePermissions`:

`secrets`:: TLS private keys, keystores, and password files (including KMS credentials such as Vault tokens, AWS access keys, and Azure client secrets via `FilePassword`).
Default: `DISABLED` (will change to `STRICT` in a future release).

`truststores`:: TLS truststore files.
Default: `DISABLED` (will change to `RELAXED` in a future release).

`platformCredentials`:: Platform-managed credential files such as AWS IRSA web identity tokens and AWS EKS Pod Identity authorization tokens.
These are injected by cloud provider webhooks and the user cannot control their permissions.
Default: `DISABLED` (will remain `DISABLED`).

.Configuration fragment with per-category policies
[source,yaml]
----
security:
  filePermissions:
    secrets: STRICT
    truststores: RELAXED
    platformCredentials: DISABLED
----

When a category is omitted from the configuration, its default value is used.
When the entire `security.filePermissions` section is omitted, all categories use their default values.

== What is checked

When a non-`DISABLED` policy is configured for a category, Kroxylicious checks permissions before reading any file in that category:

* `secrets`: TLS private key files, keystore files, and password files referenced by `FilePassword` providers
* `truststores`: TLS truststore files
* `platformCredentials`: AWS IRSA web identity token files and AWS EKS Pod Identity authorization token files

If a file fails the permission check, Kroxylicious throws a `FilePermissionViolationException` and the proxy fails to start.

== Exit code

When the proxy fails to start due to a file permission violation, it exits with code 78 (`EX_CONFIG` from sysexits.h) instead of the generic exit code 1.
This distinct exit code allows the Kubernetes operator to determine _why_ the proxy crashed by inspecting the pod's terminated container status, without reading logs.

== Making files compliant

To restrict a file to owner-only access (`STRICT`):

[source,bash]
----
chmod 600 /path/to/private.key
chmod 600 /path/to/keystore.p12
chmod 600 /path/to/password.txt
----

== Kubernetes considerations

Kubernetes mounts `Secret` volume files as `root:root 0644` by default, which is world-readable.
The Kroxylicious Operator automatically sets the pod security context so that secret files can be read with restricted permissions:

* `fsGroup: 185` - Kubernetes changes the group ownership of mounted secret files to GID 185 (the `kroxylicious` user's GID in the proxy image).
* `runAsGroup: 185` - The proxy container process runs with GID 185, allowing it to read files owned by that group.
* `defaultMode: 0440` - Secret volumes are mounted with owner+group read-only permissions, preventing world-readable secrets.

On OpenShift, `fsGroup` and `runAsGroup` are omitted because the `restricted-v2` SCC's `MustRunAs` strategy automatically injects the namespace-allocated GID.

With these settings in place, the `RELAXED` policy is suitable for operator-managed deployments.
The operator defaults to `secrets: RELAXED`, `truststores: RELAXED`, `platformCredentials: DISABLED` when no policies are explicitly configured in the `KafkaProxy` resource.

=== Operator status condition

When the proxy crashes due to a file permission violation, the operator sets a `FilePermissionsValid` condition on the `KafkaProxy` resource:

* `FilePermissionsValid=True` - the proxy is running or no permission violation has been detected.
* `FilePermissionsValid=False` with reason `FilePermissionsViolation` - the proxy crashed with exit code 78.
The condition message contains the error detail.

The condition clears automatically when the proxy restarts successfully after the permissions are corrected.

You can inspect the condition with:

[source,bash]
----
kubectl get kafkaproxy simple -o jsonpath='{.status.conditions}'
----

=== Configuring per-category policies in the KafkaProxy CRD

The `KafkaProxy` CRD exposes per-category file permission policies at `spec.security.filePermissions`:

[source,yaml]
----
apiVersion: kroxylicious.io/v1alpha1
kind: KafkaProxy
metadata:
  name: simple
spec:
  security:
    filePermissions:
      secrets: RELAXED
      truststores: RELAXED
      platformCredentials: DISABLED
----

When running the proxy directly on Linux (not via the operator), use `STRICT` for secrets and ensure secret files have owner-only permissions:

[source,yaml]
----
security:
  filePermissions:
    secrets: STRICT
    truststores: RELAXED
----
